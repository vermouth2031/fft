# 板上 SD 启动文件维护

SD 卡保持插在 Zybo Z7-20 上，使用 USB JTAG 将维护程序临时下载到 DDR。
只安装当前构建的 `artifacts/BOOT_udp.BIN`，目标为 SD 根目录 `BOOT.BIN`。
不修改分区、不格式化、不删除其他文件；维护程序本身不会写入启动镜像。

必须先完成统一构建、Bootgen 来源校验、新版 JTAG 部署及完整实板数值验收。
程序从 `reports/software_validation.json` 找到本次 Vitis workspace 和 BSP，
只读取其头文件/库，所有新编译输出位于 `build/maintenance/`。

```powershell
# 只准备独立编译配置，不编译、不连接板卡。
python scripts/maintenance/sd_boot_update.py prepare

# 离线编译维护 ELF，不连接板卡。
python scripts/maintenance/sd_boot_update.py build

# 真正写 SD：子命令和 --write 缺一不可。
# --reboot 在完整读回 SHA-256 一致后检查 SD 启动模式、复位并核验网络版本。
python scripts/maintenance/sd_boot_update.py write --write --reboot
```

写入流程：停止采集 → JTAG 初始化 PS/DDR → 下载维护 ELF 与镜像 → 校验下载 →
写入随机且尚不存在的 `Nxxxxxxx.BIN` → 关闭、重新打开、完整读取并逐字节比较 →
将原 `BOOT.BIN` 改名为同编号且尚不存在的 `Bxxxxxxx.BIN` → 安装新 `BOOT.BIN` →
再次完整读取并比较 → JTAG 导出所有读回字节 → 主机 SHA-256 比较。
只有最后检查通过，才可执行可选的 SD 启动复位。

保留的 `Bxxxxxxx.BIN` 是原启动文件；成功后也不会自动删除。
新文件安装或验证失败时维护程序尝试恢复原文件，回滚状态写入 mailbox。
FAT 的两个重命名操作不构成掉电原子事务，因此操作期间应保持供电。
超时会留下 CPU 继续运行，先检查状态，不应立即复位或断电。

DDR 分配：维护 ELF `0x00100000..0x00ffffff`；mailbox `0x0ff00000`；
输入镜像 `0x10000000`；完整读回 `0x12000000`；镜像上限 16 MiB。
维护程序关闭 I/D cache，并在软件与主机分别检查长度、CRC32 和完整内容。

每次执行产生独立日志、mailbox、读回文件和结果 JSON，并更新
`reports/sd_boot_update.json`。不会修改 `reports/current_deployment.json` 或
`reports/current_board_validation.json`。SD 复位后核对网络版本，并实际执行一组数字零矩形突发的完整数值核验；这项有限复核不代替此前完整套件，原 JTAG 实测关联保持不变。

## SD 自动测试固件的独立实板验收

这一步应放在新版统一构建之后、正式 UDP JTAG 部署和完整网络验收之前。
它运行当前实际 `iq_sd.elf`，该程序仅新建一个 `RUNxxxx` 保存 16 例结果；
不改 `BOOT.BIN`、已有运行目录或 `VECTORS`，也不需要串口可用。

```powershell
python scripts/maintenance/validate_sd.py --prepare
python scripts/maintenance/validate_sd.py --build
python scripts/maintenance/validate_sd.py --out captures/sd_20260918_new
```

前两步离线，最后一条执行三次有日志的 `rst -system -stop`：只读导出原目录及
8 个向量 → 下载当前 bit 与实际 SD 应用，等待其文件关闭后的完成行断点 →
再次运行只读 helper，导出新增目录的 META/FREQ/BURST/SNAP 原始文件。
helper 仅使用 FatFs 目录枚举及只读打开/读取接口，将文件打包到 `0x12000000`
供 JTAG 导出；逐文件和整个包校验 CRC32，主机建立 SHA-256 清单。

现有向量缺失或与当前参考不符时停止，不自动补写。程序对比新增 RUN 目录集合、
核验新版元数据，调用 `host/analyze_sd.py` 的实际数值解析，再核对可用快照。
结果保存在 `reports/current_sd_validation.json` 及指定 captures 目录，包含当前
bit/XSA/SD ELF 散列、所有原始文件和 16 例数值结果。它证明 SD 应用实际运行，
不证明从 SD BOOT 启动；不会改写 UDP 部署或完整网络板测报告。

结束后板卡停在只读 helper，按正式 `scripts/deploy_board.py` 重新部署网络固件。
